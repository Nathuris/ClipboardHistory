- ✅ 复制图片 → 图片文件保存，数据库记录路径

**❌ 未完成说明（3.5）**：`DatabaseManager.isDuplicate(text:)` 方法已经写好，但**从未被任何地方调用**（`ClipboardMonitor` 里没有去重判断）。

**实际影响评估（2026-09-21 实测）**：
- 机制已确认：向系统剪贴板写入两次相同内容，系统编号（`changeCount`）**会**递增，而监听器正是靠比对编号来判断「有新内容」。因此连着复制同一内容两次，**确实会产生 2 条重复记录**。
- 但查用户真实数据库（`~/Library/Application Support/ClipboardHistory/clipboard.db`）：6 条文字记录内容各不相同，**重复记录 0 条**。说明日常使用中极少触发（用户几乎不会连着复制同一个东西）。
- 结论：属**潜在缺陷**，非正在发作的故障。优先级定为 🟡 中。

> 注：`ClipboardMonitor.ignoreNextChange()` 只解决「点击历史条目粘贴时不要把自己再记一遍」，与 3.5 要求的「用户连续复制同一内容去重」是两回事。
> 需求来源：`docs/requirements.md` 第 25 行「去重：连续复制同一内容不重复记录」。

**✅ 9.3 已于 2026-09-21 修复**。原实现是一个**假开关**：只在 `UserDefaults` 里记「开/关」，从不调用任何系统接口，用户拨了它重启后软件并不会自动运行。

现改为（新增 `Services/LaunchAtLogin.swift`）：
- 开关状态**直接读系统的 `SMAppService.mainApp.status`**，不再存 UserDefaults
- 拨动时调用 `register()` / `unregister()`，并把系统返回的真实结果回填界面
- 注册失败时弹窗给出中文原因，不会出现「界面显示开了、实际没开」
- 处理「已登记但被系统拦下、需用户批准」的状态，并提供跳转到系统设置的按钮

**实测验证（2026-09-21）**：用与本 App 完全相同的包配置（bundle id `com.clipboardhistory.app`、ad-hoc 临时签名、位于 `~/Applications`）实测，`register()` **成功**，状态由 `notFound` 变为 `enabled`，`unregister()` 后回到 `notRegistered`。
> **重要发现**：对于**从未登记过**开机自启的 App，系统 `status` 返回的是 `.notFound` 而非 `.notRegistered`。因此 `.notFound` 属正常初始状态，不能当作错误报给用户——否则每个第一次打开该设置页的人都会看到一句吓人的报错。

**🔄 9.4 部分完成**：已实现「登记被系统拦下时」的引导（提示文字 + 跳转系统设置按钮）。但需求 `requirements.md` 第 83 行要求的「**首次启动时询问用户是否开启**」尚未实现——目前用户必须自己打开设置才能看到这个开关。

## 补充修复 — 设置窗口把内容裁掉（2026-09-21 发现并修复）

**这不是任务清单里的项目，是排查「开机自启开关消失了」时挖出来的隐藏缺陷。**

**现象**：设置 → 通用 页里，「启动」一栏的开机自启开关**根本看不见**。页面底部只露出「启动」两个字的标题，下面的开关被整个裁掉。

**原因**：`SettingsWindow.swift` 给每个标签页写死了固定高度：

```swift
GeneralSettingsView()
    .frame(width: 400, height: 250)   // ← 只给 250 点高
```

而实测「通用」页内容**实际需要 323 点**高，超出 73 点。那 73 点正好是「启动」一栏所在的位置。

| 页面 | 内容需要 | 窗口给了 | 结果 |
|------|----------|----------|------|
| 通用（开关在这页） | 323 点 | 250 点 | ❌ 裁掉 73 点 |
| 快捷键 | 187 点 | 250 点 | ✅ 正常 |
| 关于 | 280 点 | 250 点 | ❌ 裁掉 30 点（底部「退出应用」按钮） |

该缺陷自 2026-07-13 写下 `GeneralSettingsView` 起就存在，用户装过的每个版本都有。

**修复**：删除各标签页写死的高度，改由 TabView 保证最小空间（`minWidth: 440, minHeight: 440`），各页按自身内容自然撑开；`AboutView` 内部写死的 400×280 一并去掉。修复后用离屏渲染逐页复核，确认内容完整可见。

> 排查方法留档：把 SwiftUI 视图用 `NSHostingController` 渲染成图片、并用 `fittingSize` 量出实际所需尺寸，可以**在不启动 App 的情况下**验证界面是否会被裁切。以后改设置界面可沿用。
